# 기여 가이드

이 문서는 프로젝트의 브랜치 운영 방식과 커밋 메시지 작성 규칙을 안내합니다. 모든 기여자는 아래 규칙에 따라 작업합니다.

## 브랜치 운영

프로젝트 규모와 별도의 개발 서버가 필요하지 않은 운영 환경을 고려하여, `main`과 작업 브랜치로 구성된 간단한 브랜치 전략을 사용합니다.

| 브랜치 | 용도 |
| --- | --- |
| `main` | 작업 결과를 통합하는 기본 브랜치 |
| `feat/*` | 기능 개발 및 기타 작업을 수행하는 브랜치 |

작업 브랜치는 `feat/작업명` 형식으로 작성하며, 작업 내용을 알아볼 수 있는 이름을 사용합니다.

예시:

- `feat/login`
- `feat/update-contributing`

## 커밋 메시지

커밋 메시지는 다음 형식으로 작성합니다.

```text
유형: 주요 변경 내용
```

주요 변경 내용은 한 줄로 간결하게 작성하며, 무엇을 변경했는지 명확히 설명합니다.

| 유형 | 용도 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 및 오류 수정 |
| `docs` | 문서 작성 및 수정 |
| `refactor` | 기능 동작을 유지하면서 코드 구조 개선 |
| `chore` | 개발 환경 및 설정 변경 |
| `test` | 테스트 코드 추가 및 수정 | 

예시:

```text
feat: 로그인 기능 추가
fix: 로그인 실패 시 오류 메시지 수정
docs: 기여 가이드 작성
refactor: 사용자 입력 검증 로직 정리
```

## PR 작성 규칙

- PR 제목은 커밋 메시지와 같은 `유형: 주요 변경 내용` 형식으로 작성합니다.
- 본문은 PR 템플릿의 변경 사항(What), 변경 이유(Why), 테스트 및 검증 방법(How)을 모두 채웁니다.
- 관련 이슈는 본문에 `Closes #이슈번호`로 명시합니다.
- 리뷰어 1명 이상의 승인(Approve)을 받은 뒤 병합합니다.

## 코드 리뷰 규칙

- "LGTM", "좋아요"만 남기는 리뷰는 금지하며, PR마다 실질적인 코멘트를 1개 이상 남깁니다.
- 코멘트는 특정 라인이나 파일을 근거로 질문, 대안 제안, 리스크 지적, 개선 제안 중 하나를 포함합니다.
- PR 작성자는 리뷰 코멘트에 답글 또는 수정 커밋으로 응답합니다.

## 충돌 대응 흐름

충돌 발생 → 공유 → 해결 → 기록 순서로 대응합니다.

- 누가: 충돌이 발생한 PR의 작성자가 해결을 주도합니다.
- 어떻게: 충돌 상대에게 공유한 뒤 함께 해결 방향을 정합니다.
- 어디에: 해결 과정을 `docs/conflict-resolution.md`에 기록합니다.
